#### PUSH-1 detail — Web Push notifications via installed PWA

**Platform support**: Android has long supported Web Push for installed PWAs. iOS added it in 16.4 (2023), but *only* for a site added to the Home Screen — not for Safari tabs. `public/manifest.json` already has `display: "standalone"` + icons configured, so the app is already installable; only the push-specific pieces below are new. The real-world limiter is discoverability — iOS has no native "install" prompt like Android's `beforeinstallprompt`, so a user has to manually tap Share → Add to Home Screen before push can ever work for them; a UI nudge (detect non-standalone via `navigator.standalone` / `matchMedia('(display-mode: standalone)')`, show an "Add to Home Screen to get notifications" banner) is needed to drive that.

**New pieces needed**:
1. **Service worker** (`public/sw.js` or similar, registered from `main.jsx`) — none exists today. Listens for `push` events → `self.registration.showNotification()`; handles `notificationclick` to deep-link into the relevant screen (chat thread, bet, etc.).
2. **VAPID keypair** — one-time, self-generated (`web-push` npm package locally), stored as a Supabase secret. No third-party account.
3. **New migration** — `push_subscriptions` table (`user_id`, `endpoint`, `p256dh`, `auth`, `created_at`), RLS: a user can insert/delete their own rows only.
4. **Client subscribe flow** — a permission-request toggle (natural home: `SettingsScreen.jsx`) calling `Notification.requestPermission()` then `registration.pushManager.subscribe({ applicationServerKey: VAPID_PUBLIC_KEY })`, upserting the resulting subscription into `push_subscriptions`.
5. **Send-side Edge Function** (`send-push-notification`, new) — the good news: `clubhouse_notifications` (schema.sql, 4 existing `INSERT` sites — `dispute_freeform_result` and 3 others around lines 5665/5693/5720) already centralizes in-app notification fan-out for `p2p_challenge`/`league`/`paddock`/`box`/`clubhouse` source types (bets, challenges, arbitration, etc.). Wiring a Postgres trigger (or a Supabase Database Webhook) on `INSERT INTO clubhouse_notifications` → `send-push-notification` covers **all of those for free** — one integration point, no per-feature wiring.
6. **Chat is the one real gap**: `chat_messages` currently has *zero* integration with `clubhouse_notifications` — chat is pure Supabase Realtime (in-app only, nothing persisted for offline/background delivery). Getting chat pushes needs a new trigger on `chat_messages` insert that either writes a `clubhouse_notifications` row (reusing the pipeline above) or calls `send-push-notification` directly, with sensible scoping (e.g. only when the recipient isn't already an active Realtime subscriber, to avoid double-notifying an open chat window) — this is the +0.5–1 day beyond the base estimate.

**Doesn't affect the native path**: if the app ever ships to the App Store via the existing Capacitor iOS/Android projects, that would use native push (APNs/FCM) — a separate mechanism from Web Push, needing its own wiring later. This item is scoped purely to the current installed-PWA/no-App-Store case.

## 🟡 P2 — DRAFT-20: optional 20-player squads + 5-substitution cap per matchday for draft leagues (2026-10-16) — open, spec only, no PR yet

**Origin**: user suggestion, reviewed 2026-10-16. Draft ("noduplicate") leagues only; classic leagues and in-flight leagues are untouched.

**Agreed rules**
- **Squad size is optional**: 15 (current) or 20, chosen when the draft league is created. Both stay valid.
- **20-player split** (`position_limits`): GK 2 / DEF 7 / MID 7 / FWD 4. 15-player split stays GK 2 / DEF 5 / MID 5 / FWD 3. Starting XI rule is unchanged (exactly 1 GK, ≥1 DEF/MID/FWD, 11 total), so the bench is 9 at size 20.
- **Budget**: €130M for a 20-player squad. Product view: budget is not a binding constraint in draft leagues (top players get taken, money is left over), so no further balancing is needed.
- **Club cap** stays 3 per club (`club_cap_default`).
- **Transfers** stay unlimited in draft leagues (`process-transfer` already skips the per-round limit for `noduplicate`); the whole squad can be changed.
- **Substitution cap = 5 per matchday.** A substitution is an XI↔bench swap made through `set_lineup`.
  - Before the round's kickoff the lineup is team management: **no limit, any number of changes, nothing counted.**
  - After kickoff each swap counts toward the cap of 5. Existing rules already prevent re-entry: a player subbed out after his match started is locked for the round (`lineup_locks`), and a player whose match has started or finished cannot be subbed in. So there is no swap-and-swap-back loophole to special-case.
  - Auto-subs at round end (`applyAutoSubs`, 0-minute starters) are system actions and are **not** counted.

**Technical plan**
1. **Migration (next free number 301+)**: new `league_config` key `max_lineup_subs` (null = unlimited; seeded 5 for new draft leagues only); updated `create_league` seeding / league-creation path to take `squad_size` 15|20 and set `squad_size`, `position_limits`, `draft_position_caps`, `draft_list_size` (≈3× squad size — see migrations 159/160 for the prior mismatch) and `budget_total` accordingly. Needs the pre-migration backup and an explicit "yes, run it" before applying.
2. **`set_lineup`** (latest version: migration 214): after the existing validations, if the round's first kickoff has passed and `max_lineup_subs` is set, count this squad's post-kickoff `lineup_swap` events for the matchday (`squad_events`, migration 183) and reject at the cap with a clear error code; otherwise log the swap as usual. Server-authoritative, so it cannot be bypassed from the client.
3. **Hardcoded 15s to remove**: `process-transfer/index.js:278` (`currentPlayers.length < 15`), `LeagueScreen.jsx` (~1446–1454), `GazetteDraftReport.jsx:267`, `CommissionerPanel.jsx` copy (lines ~118, 2195, 3031), `ScoringInfoModal.jsx:79`, `OnboardingWizard.jsx:25` fallback. Default `15` fallbacks in `useLeagueConfig`, `wishlistDraft.ts`, `claim_draft_player` and the auction functions are fine as fallbacks.
4. **UI**: squad-size option in `NewCompetitionFlow.jsx` (draft only); `SquadScreen`/`LiveScreen` bench list sized for 9; "Subs used n/5" counter, swap disabled at 5 and toast on server rejection.
5. **Docs/tests**: update `ScoringInfoModal` and `docs/architecture/DRAFT_SYSTEM_DESIGN.md`; add `platform.spec.js`/unit coverage for the cap and a 20-player draft dry run.
6. **Edge Functions**: only redeploy if a function file changes (likely `process-transfer`); Vercel does not auto-deploy them.

**Risks to check before shipping**
- **Pool depth**: no-duplicate draft needs managers × squad size unique players (10 managers × 20 = 200). Fine for a full World Cup/UCL pool; check short tournaments and knockout stages with eliminated clubs. `calculate_relaxation_state` already reads `squad_size`, so pressure (and relaxation tiers) will rise earlier — simulate (read-only) against the real pool first.
- **Draft length / wishlist**: more picks per manager; verify `run-wishlist-draft`, lottery and reverse-standings draft fill 20 slots within position caps and the 3-per-club cap, including the formation floor safety net.

**Open questions (confirm before build)**
1. **What counts as "after kickoff"?** (a) the round's first kickoff — any swap after that counts, even between two players whose matches haven't started; or (b) per player — a swap counts only if the outgoing player's match has started/finished (consistent with the per-fixture lock model; swapping two not-yet-played players stays free). Recommendation: (b).
2. **Budget for a 15-player draft league**: assumed to stay at €100M; confirm.
3. **In-flight draft leagues**: out of scope for v1. Converting one later (raise `squad_size` to 20 / budget to €130M, managers top up via market) is possible but needs a per-league data write with SELECT-first approval, a fairness rule for the 5 extra slots, and a pool-depth check.

## 🟡 P3 — Fallback conceded-penalty is silently always 0 due to a field-name mismatch — open, no PR yet (2026-09-06, found during Scoring v3 Phase 1)

`FALLBACK_POINTS` in [calculate-scores/index.js](supabase/functions/calculate-scores/index.js) names the goals-conceded-penalty field `conceded_per_goal`, but [scoring-logic.js](supabase/functions/calculate-scores/scoring-logic.js)'s `scorePlayer`/`buildBreakdown` reads `rules.conceded_2plus_penalty` — so any tournament falling back to `FALLBACK_POINTS` (no `scoring_rules` DB row, e.g. a future EPL/426 tournament) silently never applies the conceded-goals penalty for GK/DEF, with no error. Pre-existing bug, not introduced by Phase 1 — found while auditing the fallback constants for that PR, deliberately left out of its scope. Fix: rename `conceded_per_goal` → `conceded_2plus_penalty` in `FALLBACK_POINTS` (both GK and DEF rows currently have it at value `0` anyway, so no scoring change today — but the field name needs to match before that value is ever made non-zero, or before a tournament without a DB row goes live).

## 🟡 P2 — Forza tournament IDs are reused every season — no durable season-boundary handling (2026-09-01) — open, no PR yet

**Context**: Preparing to load UEFA Champions League 2026-27, discovered `tournaments.forza_id=1593` was still carrying **all of last season's** (2025-26) data — 281 stale fixtures and ~3,400 players from clubs no longer in this year's competition, still `sync_enabled`-adjacent in the DB even though the season had ended. Forza does not mint a new tournament ID per season — it reuses the same `forza_id` and just rolls `current_season` forward internally, while its `round` field resets to 1 each season. Under our schema, `round_number` (and the derived `matchday_id = '{forza_id}-r{round_number}'`) is scoped only by `tournament_id`, not by season — so once a new season's fixtures land on top of an old season's under the same forza_id, round numbers collide (e.g. two completely different sets of 18 matches both claiming to be "round 1"), and `sync-players`' team list (derived from *all* current `fixtures` rows for that `tournament_id`, not season-filtered — see [supabase/functions/sync-players/index.js](supabase/functions/sync-players/index.js)) gets contaminated with stale clubs, pulling in retired/relegated teams and their full squads.

**What was done this session (manual, one-off fix — not a platform fix)**: confirmed the season boundary was clean (old season's last kickoff 2026-05-30, new season's first kickoff 2026-07-07, no overlap), backed up the affected rows to `backups/ucl_1593_*_20260901_121817.json` (Docker was down, so used the CLAUDE.md-documented SELECT-and-save fallback instead of `supabase db dump`), then deleted the 281 old-season fixtures, ~1,418 players tied to the 47 old-season-only clubs (targeted delete, not delete-all, to preserve `price` valuations already set on current-season players), and 7 stale `matchday_deadlines` rows, and updated the `tournaments` row's `name`/`slug`/`starts_at`/`ends_at` to the 2026-27 season. Verified clean afterward: 234 fixtures, rounds 1–8 each with exactly 18 fixtures (no collisions), 2,395 players across 80 clubs, and World Cup (`tournament_id='429'`) confirmed untouched throughout (104 fixtures, never referenced by any query this session).

**The open problem**: this was done by hand, tournament-by-tournament, and nothing prevents the same collision from recurring — for UCL next season, and for any other tournament that reuses its forza_id year over year (continental/knockout competitions are the likely repeat offenders; single-season domestic leagues like a given EPL season may or may not follow the same pattern — not yet confirmed either way). There is no season-aware cleanup step in [docs/deployment/ADDING_A_NEW_TOURNAMENT.md](docs/deployment/ADDING_A_NEW_TOURNAMENT.md)'s onboarding cookbook, and no code path detects "this forza_id's fixtures just changed season out from under us."

**Suggested direction (not scoped/estimated yet)**: either (a) detect a season rollover automatically — e.g. `sync-fixtures` compares the API's `current_season`/season-start date against the DB's last-known value for that `forza_id` and, on mismatch, purges/archives the prior season's fixtures+players+deadlines before upserting the new batch, or (b) make season part of the schema's identity for recurring tournaments (e.g. a `season` column feeding into `matchday_id` instead of relying on `tournament_id` alone) so old and new season data can coexist without collision instead of requiring deletion. Either approach needs to happen without ever touching a different tournament's rows (this session's `429`-must-stay-untouched constraint should generalize: any season-rollover logic must be scoped tightly to the one `forza_id` being rolled over).

**Priority**: P2 — not urgent (this season's UCL data is now correct and playable), but will recur automatically next season unless addressed, and would then block onboarding for whichever tournament hits it, the same way this session's prep work was blocked until manually fixed.

**Cross-reference (2026-09-13, PR #1022)**: this same gap is exactly why `tournaments.status` auto-completion was explicitly *not* built when adding a Clubhouse "finished" indicator — see the completed-work entry above. A recurring tournament's season-end fixtures all legitimately go `finished`, which would falsely trigger `status='completed'` with no signal to flip back once the next season's fixtures land in the same row. `status` remains a manual, one-off field until this P2 item has a real fix; any future work on this item should also revisit whether `status` can then be safely automated.

## 🟡 P2 — `award-season-trophies` cron will never see a completed World Cup once turned on (2026-09-13, open, no PR yet)

**Context**: found while marking the WC 2026 tournament `status='completed'` this session (see the completed-work entry above). `award-season-trophies`'s football branch filters on `status='active' AND ends_at < now()` — a tournament that's already flipped to `status='completed'` (like WC now) permanently falls outside that filter. The cron itself is currently `active=false` (frozen, per prior session notes), so this hasn't caused a missed award yet — but the moment it's turned on, it will never award WC's season-champion trophies, because WC no longer matches its own filter.

**Suggested direction (not scoped/estimated yet)**: update the football branch's filter to `status IN ('active', 'completed')` (or equivalent), so a manually-completed tournament still gets picked up for one-time trophy awarding. Needs a guard against re-awarding on every run once a tournament's trophies are already granted (check whatever existing idempotency the cron uses for `active` tournaments, e.g. a `trophy_ledger` existence check, still applies here).

**Priority**: P2 — not urgent while the cron stays frozen, but must be fixed before `award-season-trophies` is turned back on, or WC 2026 (and any other tournament marked `completed` by hand) will silently never get its trophies awarded.
